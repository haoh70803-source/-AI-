# 项目 Agent 运行优化（2026-10-09）

本轮目标：让创作协作能够直接交付可用作品，可靠使用资料和持久历史，并为内部团队和客户使用提供成本可控的缓存、并发保护与流式反馈。遵循 PRODUCT.md / ARCHITECTURE.md；没有修改治理规则、业务数据库 Schema 或执行 migration。

## 回复与创作

**CURRENT IMPLEMENTATION**：项目 Agent 提示词采用以下规则：

- 在权限、事实和安全边界内，优先遵循本轮明确要求。
- 信息足够就交付成果；缺少关键输入只做最少询问；用户需要模板时才提供模板。
- 常规角度、结构、表达和可逆修改由 Agent 判断，不在每次回复末尾追加确认或选择。
- 使用资料提炼、比较和重新组织内容，保留创作空间；不把外部案例或历史 AI 回复写成用户的真实经历。
- 验收关注用户仍需要补做多少核心工作，不能用占位符和空框架代替成稿。

提示词变更属于行为约束，自动化服务测试不等于真实模型已稳定遵循。原始审计和创作验收案例见 [审计文档](audit/workbench-agent-audit-2026-10-09.md)。

## 资料与持久历史

**CURRENT IMPLEMENTATION**：用户选中的资料优先获得上下文预算；授权的飞书检索默认补充相关知识。明确要求不用飞书、只使用选中内容，或简短的局部改稿时，会跳过默认飞书检索。自动检索目前使用已有关键词检索能力，不是新增向量检索系统。

持久历史召回复用 PostgreSQL 中已有的 AssistantMessage：

1. 服务端核对当前用户、工作空间、项目、对话及成员有效状态。
2. 最近 10 条消息继续作为直接对话上下文；额外从更早的已完成记录中找回偏好和本轮相关讨论，不限于最近 40 条。
3. 用户偏好和相关记录最多各 6 条，总计不超过 6000 UTF-8 字节，完整记录不会被截成误导片段。
4. 历史记录携带原始角色、时间和来源。本轮要求优先，较新的用户要求覆盖旧要求；历史文本不会自动升级为已确认事实。

记忆限定在当前用户当前项目的主对话；不会自动继承其他用户或项目的内容。该版本不是独立的结构化事实库，检索也可能漏掉没有匹配关键词的旧讨论。超大单条记录超出预算时会被省略。

**CURRENT IMPLEMENTATION GAP**：结构化的确认、修正、撤销、记忆管理界面及语义召回尚未完成。本轮没有宣称已实现完整长期记忆产品。

## Redis 缓存与降级

**CURRENT IMPLEMENTATION**：缓存只加速检索，不缓存整篇创作回复。这样重复问题仍会结合本轮资料重新创作。

| 缓存 | 内容 | 有效期 | 命中后的检查 |
| --- | --- | --- | --- |
| 历史召回 | 消息 ID 列表 | 60 秒 | 重新核对成员与对话权限，从数据库读取当前记录。 |
| 飞书检索 | 片段 ID 列表 | 30 秒 | 重新核对成员、连接版本、文档可用状态及校验时间，从数据库读取当前内容；无效时重新检索。 |

缓存键包含工作空间、用户及检索条件；历史召回还包含项目、对话和历史版本。Redis 不可用时回退原检索，连接/命令超时为 300ms，失败后暂停重连 30 秒。缓存不能绕过权限检查，也不作为长期数据的唯一存储。

优先使用 `ASSISTANT_REDIS_URL`，未设置时复用 `REDIS_URL`；离线审阅模式不连接缓存。

本地专用缓存配置见 [docker-compose.agent.yml](../docker-compose.agent.yml)：仅绑定 127.0.0.1:16380，缓存上限 64MB，容器上限 128MB，采用 LRU 淘汰，不做持久化。启动：

```powershell
docker compose -f docker-compose.agent.yml up -d
```

工作台启动环境配置：

```dotenv
ASSISTANT_REDIS_URL=redis://127.0.0.1:16380/0
```

本次已在本机私有启动配置中设置该地址。原 Worker 使用的 REDIS_URL 保持独立，因此 Agent 缓存启动不表示后台采集、转写队列已恢复。

## 多用户保护

**CURRENT IMPLEMENTATION**：主项目 Agent 在创建生成记录的同一事务中进行准入检查，复用 PostgreSQL 短事务锁，跨 Web 实例共享状态；Redis 故障不会使并发限制失效。已有同一对话只允许一个运行中请求的规则继续保留。

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| ASSISTANT_GLOBAL_CONCURRENCY | 32 | 所有实例主项目 Agent 的同时生成上限。 |
| ASSISTANT_WORKSPACE_CONCURRENCY | 8 | 单工作空间同时生成上限。 |
| ASSISTANT_USER_CONCURRENCY | 2 | 单用户在一个工作空间内同时生成上限。 |
| ASSISTANT_REQUESTS_PER_MINUTE | 20 | 单用户在一个工作空间内每分钟请求上限。 |

配置必须是 1–10000 的整数，否则回退默认值。默认值是保护设置，不是已证明的吞吐能力，部署时须依据数据库连接数、供应商配额和压测结果调整。

达到上限时返回可重试的 RATE_LIMITED 提示，不建立新生成记录，不自动排队或自动重试付费模型。频率额度在并发准入之前消耗，重复提交被拒绝的请求也计入频率。

运行记录每 30 秒更新存活时间，10 分钟未更新的记录不占准入额度。下一次进入同一对话时，旧运行记录会被标记超时失败。SSE 主入口有 5 分钟处理时限。

**BOUNDARY**：这些准入规则接入主项目对话；旧 Canvas 节点生成、其他模型调用和 Worker 任务没有统一接入本次限流，不据此宣称全系统并发治理已完成。跨租户范围仍由服务端权限检查保证，不能用提示词替代。

## 流式体验

**CURRENT IMPLEMENTATION**：沿用模型正文的流式输出，补充真实历史读取状态、SSE 连接确认、15 秒连接心跳和禁止代理缓冲的响应头。用户可以先看到当前执行阶段，再逐段看到正文，不需要等待整篇生成结束。

展示的是读取资料、找回历史、生成、检查等实际工作进度，不展示模型内部推理。连接取消会中止请求；生成失败、主动停止或超时会保留已生成正文并释放运行额度。模型超时记为 FAILED / TIMEOUT，主动停止记为 STOPPED。

SSE 建立以后，限流等错误通过流内 error 事件传递；客户端应识别错误码，不能只依据 HTTP 200 判断任务成功。生产反向代理仍需要核对是否允许流式传输和足够的连接时限。

## 本轮验证与后续上线门槛

**VERIFICATION**：直接相关自动化测试覆盖持久历史召回、权限撤销后的缓存读取、缓存版本/范围、Redis 故障降级、并发准入、SSE 分段与心跳、取消及错误反馈。真实 Redis 使用独立测试逻辑库，数据库集成使用独立测试数据库。

本轮最终执行结果：8 个相关测试文件、41 项测试通过；Web TypeScript 检查通过；本次 Agent 文件定向 ESLint 通过。3022 工作台已重启加载配置，入口返回 200、未登录 Agent 请求返回 401、就绪检查显示数据库和存储正常及外部调用启用，专用 Redis 返回 PONG。没有运行全仓 build、全仓测试、浏览器 E2E 或正式吞吐压测；没有用 Mock 结果宣称真实模型质量已验收。

并发集成测试验证：6 个同时请求、容量设置为 3 时，只准入 3 个、拒绝 3 个，任务完成后释放额度。这证明准入行为，不证明 32 并发容量或企业级吞吐。

**CURRENT IMPLEMENTATION GAP**：正式企业上线还需要目标负载压测、真实模型质量回归、供应商失败/配额验证、部署环境流式链路验收、监控报警和备份恢复验证。结构化记忆和全调用入口的统一容量治理是后续明确任务；本轮没有扩展许可证、桌面交付或其他产品域。

维护时优先复用现有数据库、权限、Provider 和 Redis 能力；缓存允许丢失，核心记录可追溯。不引入额外向量数据库或自动多模型重试作为这一版的必要部署条件。

**GIT**：未暂存、提交或推送，交付停在 READY_TO_STAGE；用户既有改动保留。文档不授权部署到客户环境或提前扩展其他产品域。

## 多轮创作调整与企业验收（后续实施）

**CURRENT IMPLEMENTATION**：新增任务承接，复用 AssistantMessage.metadata，不增加 Schema。保存用户原始要求、首次补充与最近三次更新，最大约 16000 UTF-8 字节。消息创建与任务更新在已有准入事务内完成；复用前从同一用户项目对话重新读取来源，来源被删除时不继续沿用。明确换任务重置记录；重试按原请求之前的历史重建，避免混入后续要求。

识别换任务与改稿使用可审查的规则，不增加一次模型分类调用。规则不等于通用任务规划器，复杂或含糊的任务切换仍可能识别不准确；本轮明确要求在提示词中具有最高任务优先级。首次补充之外的较早细节可能因数量或字节上限被省略，不能宣称无限任务记忆。

模型 Provider 现在支持原生 user / assistant 历史消息，既有调用未传历史时维持原行为。主项目对话按已准入的历史 ID 发送消息；额外固定携带任务原文及用户补充，不把 AI 示例提升为用户事实。发送时移除 JSON 上下文中重复的完整对话，同时对整个实际请求（包含原生消息）执行 64000 字节上限检查。

创作提示词集中在 [prompt.ts](../apps/web/server/assistant/prompt.ts)，明确表达加工与事实新增的区别、情绪忠实、不同版本的节奏、不凑字数及自然收尾。个人日常分享默认跳过自动飞书检索；明确要求使用飞书时恢复，明确禁止时沿用禁用偏好。选中的资料仍正常读取。

**成本边界**：生产路径保持一次生成，不新增自动评审模型、付费重试或默认多模型调用。通过去除重复上下文、按需检索和复用既有缓存控制开销；没有取得账单对照，不承诺节省百分比。验证曾试用官方支持的非思考模式，但出现更多事实偏差，没有保留这项改变；当前默认模型配置保持不变。参数依据：[DeepSeek 官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)。

**VERIFICATION**：最终直接相关 10 个文件、73 项功能测试通过，覆盖连续补充、跨最近窗口的任务要求、来源删除、原生消息顺序、权限、缓存、并发、停止和流式错误处理。真实模型测试独立启用，不随常规测试自动产生费用；仅只读获取业务模型配置，创建和清理隔离测试数据库中的项目。

真实 DeepSeek 多轮样例有成功也有失败，不能以最后一次有限规则检查通过宣称稳定质量。最后一次使用 deepseek-flash，两轮约 11.15 秒；输入 Token 为 1247 / 1350，输出 Token 为 136 / 1789（包含供应商计入的输出用量，不等于正文长度）。这只是一例观测，不是延迟或容量 SLA。

**CURRENT IMPLEMENTATION GAP / 企业交付质量门槛未通过**：人工检查最后样例仍发现“到要吃的时候才发现”改变原本“煮面时发现”的时序，“没有别的”与配图中的“几根面条”没有用户依据；叙事约 70 字且带解释，仍未充分达到约 120 字自然叙事的要求。已有自动检查只覆盖部分已知偏差与重复，不能代替语义审查。当前改变可用于内部试用和后续评估，不能据此宣布对客户的企业级创作质量已达标。

上线门槛应同时满足：多主题、多轮真实样例的语义忠实及自然度、交付完整性、用户核心返工量、取消/故障/权限测试、目标并发压测、实际成本观测与运维恢复验收。正式企业上线仍受上文记录的 Worker、全入口容量治理及运维缺口影响；本轮没有借企业上线要求提前实现其他产品域。
