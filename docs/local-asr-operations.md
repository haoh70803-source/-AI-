## 本次实际修改

`pnpm dev:live` 现有统一启动入口在启动 Web 前，自动调用已有 `scripts/start-local-asr.ps1`：检查和复用已运行的 ASR，未运行时后台启动并等待健康检查。原有手动命令保留为诊断入口。启动不安装依赖、不下载模型、不调用收费识别 API。

ASR 启动失败时输出明确错误，语音 API 继续返回真实不可用状态，其他文本和项目功能仍可启动。离线 review 和配置 check 不启动 ASR，不改变已有数据、账户、凭据和外部调用策略。

统一启动解决“重启工作台还需单独启动语音”的问题。当前没有安装 Windows 开机任务或服务，没有新增常驻重启监控；电脑开机自动启动和 ASR 崩溃后的自动重启尚未完成。现有 `release:start live` 也未自动接入 ASR。不能把本次开发入口修复视为正式上线运维验收。

## 正式上线的职责

浏览器只负责获得麦克风授权和提交录音。Web API 负责账户、工作空间权限、音频大小/格式限制及临时文件处理。ASR 在服务端执行，线上用户不需要安装 Python 或运行本机启动命令。

生产托管需要包括：

1. 服务器开机自动拉起、异常退出自动重启、日志与故障告警。
2. 部署期间安装和预下载固定依赖、模型及媒体工具；处理用户录音时不临时下载安装。
3. 分开验证进程存活、所选模型是否安装、模型是否可以真实识别；`/health.status=NORMAL` 本身不代表所选质量模式已经准备好。
4. 定向验证语音故障时的提示、重试和恢复，保护已保存项目和其他工作流。
5. 根据实际硬件重新验证质量配置与耗时；现有 profile 使用 CUDA，不能直接假定无 GPU 服务器可用。
6. 确定容量后进行并发与长时间运行验收。目前 BoundedModelRuntime 同时处理一个推理任务，繁忙时拒绝新任务；不得声称已有多用户排队或水平扩容能力。
7. 经由 HTTPS 提供公网浏览器访问，保留 Web 的服务端权限检查。

现有 Python 服务和 Provider 配置都只允许 loopback。优先保留此安全边界，将 Web/Worker 与 ASR 置于同一主机/网络命名空间。若选择相互独立的容器，容器自己的 `127.0.0.1` 不能访问另一个容器；不能直接将配置改为 `http://asr:8765` 或将 ASR 改为公网监听绕过当前检查。跨容器或远程语音服务需要明确网络、鉴权和授权来源，再决定最小适配。

托管应选择一个明确的进程所有者。Docker 的重启策略适用于容器退出后的恢复；不等于不健康状态的自动恢复。不要同时使用两套外部和容器重启管理器控制同一进程。依据：[Docker 官方自动启动说明](https://docs.docker.com/engine/containers/start-containers-automatically/)。
